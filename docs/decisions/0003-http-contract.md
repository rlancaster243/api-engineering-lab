# ADR 0003: Saved-item HTTP contract, duplicate behavior and error envelope

Logical ID: P1-ADR-002 in [`PROJECT_1_ENGINEERING_FIDELITY.md`](../PROJECT_1_ENGINEERING_FIDELITY.md) §11. The schema and error-envelope parts are implemented by `01-rest-api/app/schemas.py` and `01-rest-api/app/errors.py` and covered by contract tests. The persistence parts (database checks, constraint-specific 409 mapping, the PATCH statement) are decisions for PR-02 and PR-03 to implement.

## Status

Proposed

## Context

Project 1 exposes saved items at `/v1/items` (spec §4). Several behaviors are easy to get subtly wrong and costly to change once clients exist: what a duplicate save returns, how PATCH distinguishes "unchanged" from "clear", and what shape every error takes. FastAPI's defaults disagree with the intended contract: validation errors return `{"detail": [...]}` and echo submitted input, and unknown routes and wrong methods return `{"detail": ...}` with no request identifier.

[ADR 0002](0002-saved-item-ownership-grain.md) fixed the grain and the `UNIQUE(user_id, content_id)` invariant. It left the column details open.

## Decision

1. **Duplicate save returns `409 ITEM_ALREADY_SAVED`.** PostgreSQL's unique constraint is authoritative. There is no implicit upsert, and a repeated `POST` is not a replay of the earlier success (REQ-02). Only a violation of constraint `uq_user_content` (SQLSTATE `23505`) maps to 409; foreign-key, check and primary-key violations never do.
2. **Another user's item is `404 ITEM_NOT_FOUND`**, identical to a missing one, so existence is not disclosed.
3. **Input rules** (enforced in `app/schemas.py`; the spec §3.2 database checks must accept exactly the same values, which PR-02 implements and tests):
   - `content_id`: trim space, tab, LF, CR, FF, VT; apply Unicode NFC; 1 to 255 characters after normalization; compared exactly and case-sensitively. The trim set is explicit because Python's default `strip()` removes more characters than the database `btrim` call, which would let the two layers disagree on "blank".
   - `title` at most 200 characters and not blank; stored as submitted, not trimmed. `url` an absolute `http`/`https` URL of at most 2,048 characters with no whitespace or control characters. `notes` at most 2,000 characters.
   - Unknown fields, including `user_id` and `id`, are rejected. The server never accepts ownership from a client.
4. **PATCH:** omitted field is unchanged; explicit `null` clears it; a body with no recognized field is `422`. A non-empty body whose values equal the stored values is valid and returns `200` with the current resource and an **unchanged** `updated_at`. `content_id`, `user_id` and `id` are rejected. Implemented as one owner-scoped `UPDATE ... RETURNING` that always matches an owned row, so zero rows always means `404`.
5. **One error envelope for every error**, including framework-generated ones: `{"error": {"code", "message", "request_id", "details"?}}`. The code and status table in spec §4.5 is the contract, and `tests/test_spec_contract.py` fails when code and spec disagree.
   - `details` lists `{field, rule}` pairs for validation failures and never contains submitted values.
   - `request_id` is generated by the server for every request and returned in `X-Request-ID`. A client-supplied id is ignored, because it would put attacker-controlled text into logs and responses.
   - Every `401` carries `WWW-Authenticate: Bearer`. `405` keeps its `Allow` header.
   - Unexpected exceptions return `500 INTERNAL_ERROR` with no detail; the exception and traceback are logged with the request id.
   - A framework-raised status outside the table (for example a stray 418) is reported as `500 INTERNAL_ERROR` instead of inventing a new code. If a real need appears, add the code to the spec table first.

### Refinement of ADR 0002 (resolves the open item in the spec)

ADR 0002's attribute table lists `id` as "UUID or bigint" and lists only `notes` as optional metadata. This decision fixes `id` as a **server-generated UUID** and adds optional `title` and `url`. The grain, the key and the `UNIQUE(user_id, content_id)` invariant are unchanged, so ADR 0002 stays Accepted as written and is not reopened. Where the two differ on column detail, this ADR and the spec's schema are the more specific record.

## Consequences

### Positive

- Clients see one error shape and can branch on a stable `code`.
- Validation responses cannot leak submitted data, and 5xx responses cannot leak internals.
- PATCH outcomes are deterministic: the same body against the same state always gives the same status, body and `updated_at`.

### Negative

- The handlers replace framework defaults for the whole app. The body of an existing response changes (for example `POST /health` now returns the envelope with its `405`); statuses do not.
- OpenAPI does not yet describe the error responses or the item routes, because no real routes exist until PR-03. The spec's Gate A item "OpenAPI contracts match the specification" is **not** met by this change.
- `404` for both missing and foreign items hides permission errors from legitimate debugging. The request id in logs is the substitute.

## Alternatives considered

- **Upsert or `200` on duplicate:** hides the duplicate from the client and contradicts REQ-02.
- **RFC 9457 `application/problem+json`:** standards-based and well supported by tooling. It changes the content type and shape, and no consumer needs it yet, so it is deferred. Revisit if an external consumer requires it.
- **Trim `title` on store:** friendlier, but the spec only defines trimming for `content_id`, and silently changing stored text is a behavior to opt into deliberately.
